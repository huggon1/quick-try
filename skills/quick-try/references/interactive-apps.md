# Explore an application

Use for web apps, desktop apps, editors, visual tools, and games whose core experience depends on the interface. Select an activity the user recognizes, such as finding a useful item, arranging a small collection, or editing a draft.

Prefer an accessible official demo or task-local instance. Prepare a disposable profile/database and a small meaningful dataset if import is supported. Verify the central screen and one real action with a separate record when needed. Preserve a fresh state with choices still available.

Open the real application at the useful starting point. Explain the sample and an optional goal in one or two sentences. Let the user browse, edit, undo, or try a different direction. Navigation help is available on demand; a generated walkthrough page is unnecessary.

If login must be performed by the user, clearly hand over at that point and leave post-login checks pending. A temporary URL needs its lifetime and restart route recorded. A separate browser profile does not isolate writes to the same remote account; use actual test resources or disclose that boundary.

If only the backend is runnable, offer a developer-tool trial of that backend as a different experience, not proof of the app's interface. Do not recreate the UI to hide an unavailable target.
