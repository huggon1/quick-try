# Relevant material

Choose something the user recognizes and can judge without learning a second domain. The material should expose the selected promise in a small loop and leave meaningful choices unresolved.

Prefer: material supplied for this trial; relevant material in the current workspace; a recent task or source the user has named and made accessible; a domain-adapted public sample; then a clearly labeled synthetic sample. Memory can suggest a candidate, but verify it still exists and ask about using another workspace before exploring it. Access to a file is not permission to send it to a model provider or third-party app.

Inspect the smallest relevant portion. Pick one primary sample based on familiarity, ability to show the promised change, short turnaround, and safe copying. Describe why it fits in ordinary language. If no candidate is clear, ask for a task/topic or offer a tailored public sample; do not require the user to prepare a dataset.

Copy the minimum useful material into the trial. Keep originals untouched. Preserve the properties that matter: a search tool needs a small but varied corpus; a refactoring tool needs enough project structure and tests to operate; a writing tool needs intent and audience. Redaction or simplification that removes the central challenge makes the sample unsuitable.

Do not copy credentials, environment files, session caches, private account state, or unrelated history. Record source and transformations in the trial note. External processing belongs in the plan with the service and data scope, even when the source is locally readable.

For unfamiliar public samples, give one sentence of context so the user can judge the output. Keep an untouched starting copy and put generated results elsewhere. A synthetic stand-in may test mechanics but cannot demonstrate benefits that rely on the user's real knowledge or data.
