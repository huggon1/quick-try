# Preflight report

Read before writing the first user-facing proposal. The reader may know nothing about the target. Help them understand what it does, picture the prepared experience, choose a useful way to try it, and approve the few resources that change execution.

Keep `current`, `plan`, and `need from the user` as an internal completeness check. Do not repeat those labels in the report. Write connected prose in the user's language.

## Reader order

### 1. Explain the project

In a few plain sentences, say what the project helps someone do, how people normally use it, and what this trial could help the user decide. Explain a product term before naming an internal component. Move commit IDs, manifests, package names, and tool inventories to an optional execution note unless one changes the decision.

### 2. Say how ready the experience can be

This is the core Quick Try promise. Tell the user exactly what can be waiting for them after confirmation:

- the entry they will open;
- the software, account, service, or checkout that will be prepared;
- the sample data already loaded;
- the first action available without further research;
- what must remain running and for how long;
- where results persist and how to start fresh.

Use the status that matches reality: ready to open, prepared until a named user takeover, or blocked with useful materials completed. If login, hardware, a provider, installation, cost, or missing operation capability limits readiness, explain the cause, what it prevents, and the next viable route. Do not hide a required setup step behind "ready."

### 3. Offer ways to try it and prepared data

Offer several genuinely different scenes when the target supports them. Each option says what the user would do, what input or sample Quick Try will prepare, what they will see, and the expected hands-on time or usage. Recommend one and explain why it is a good first encounter. Do not make the user invent a use case or find suitable data before starting.

Keep the options concrete. A prompt library might support adapting one example, comparing a plain prompt with a template, repeating one prompt for stability, or asking its bundled skill to choose a style. A coding agent needs prepared repositories and tasks rather than abstract feature categories.

### 4. Explain the agent-run trial

Start with "I will prepare" or the natural equivalent in the user's language. Describe the actual sequence the agent proposes to run after confirmation. Name the input, action, inspection, revision, and evidence where they matter. Say what the user will still do after receiving the result.

Choose execution methods only after designing the sequence. Mention a tool when its availability changes the result, requires takeover, or explains a limitation. For every limit, state its cause and the conclusion it prevents. Do not turn a capability inventory into the story.

### 5. Report other users' signals

Use the useful signals actually found. For each one, say who reported it, where it appeared, what happened, and how it changes this trial. A real failure may add a check, a shared workflow may suggest a prepared sample, and conflicting reports may justify a comparison.

Search the relevant available first-party, community, and social sources before writing this section. The number of signals follows the evidence; do not pad the section to reach a quota. End with a short coverage note when an unavailable platform materially narrows what was found. Keep detailed queries and tool health in the execution record.

## Confirmation

End with the recommended scene and only the decisions that change execution. Typical decisions are the selected scene, personal versus prepared data, a paid-call limit, login or takeover, private-data use, and an accepted limitation. Record choices already made as settled. Do not ask the user to approve facts or repeat the whole report.

State what the user will receive after confirmation: the direct entry, loaded sample, saved agent results when requested, reset path, and durable guide. The first action must be obvious from the handoff. If the user would still need to find a command, choose data, or work out where to begin, the proposed preparation is incomplete.

## Writing check

Write for a curious reader, not an auditor. Use short concrete sentences and varied rhythm. Prefer "the model name is not shown, so this run cannot compare model versions" over "the model identity remains an unverified limitation." Put the useful fact before provenance details.

Remove repeated scaffolding, promotional language, abstract nouns, forced contrasts, and stock patterns such as "not only X but also Y." Avoid defensive phrases such as "cannot claim" when a direct boundary is clearer. Read the finished report once for flow: a new user should understand the project, know what will be prepared, find a scene they want to try, and see the one decision needed next.

Keep exact versions, source URLs, capability observations, cost assumptions, and authorization boundaries in the durable report or attached execution record. These details support trust without interrupting the first reading.
